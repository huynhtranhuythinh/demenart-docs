## 6. Validation methodology (tooling notes — NOT durable product rules)

Recorded here per governance (do not promote to DMA_RULES):

- **MCP `execute_sql` is autocommit-per-call** — a `BEGIN … ROLLBACK` cannot span multiple calls. A rollback-safe rehearsal must therefore be a **single `DO` block** whose terminal `RAISE EXCEPTION 'LABEL>>> %', v_out` both surfaces the accumulated evidence and forces atomic rollback. Isolation guarantee is identical to `BEGIN…ROLLBACK`.
- **Authority-gated SECURITY DEFINER writers under rehearsal** — rather than fabricating `auth.users`/`profiles` rows, impersonate an existing platform admin via `set_config('request.jwt.claims', json_build_object('sub', <super_admin auth uid>, 'role','authenticated')::text, true)`. `is_admin()` short-circuits every school-authority gate, so all six lifecycle writers run against isolated QA fixtures; everything rolls back.
- **Owner-level DDL under `execute_sql`** — this project's `execute_sql` runs as `postgres` (owner of `public.enrollments`, DB `CREATE` priv), so `CREATE EXTENSION btree_gist` and `ALTER TABLE … ADD CONSTRAINT` execute inside the rolled-back `DO` block; `apply_migration` (which commits) is used only for the authorized real migration.
