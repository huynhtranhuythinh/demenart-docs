## 2. Design approval and frozen scope

The M1 design gate was approved before build with these boundaries:

- one dedicated `SECURITY DEFINER` RPC; no generic enrollment editor;
- one-way transition only: `NULL → KNOWN`;
- human/operator-asserted date only; no inference inside the RPC;
- same-school `master_admin` / `sub_admin` authority only, with school derived server-side through enrollment → class → school;
- source enrollment row serialized with `FOR UPDATE OF e`;
- reason and evidence note required, trimmed, semantically distinct, and limited to 500 characters each;
- M3 CHECK and EXCLUDE constraints remain the final geometry/overlap backstop;
- successful correction and its audit write are atomic; audit failure rolls back the correction;
- direct client UPDATE of `start_date` is removed while legitimate non-start enrollment UPDATE privileges are preserved;
- no platform-admin bypass, batch backfill, cron, trigger reconstruction, session-derived reconstruction, frontend, or forced repair of UNKNOWN rows.

Canonical meaning is unchanged: `NULL start_date` means historical effective start UNKNOWN. `UNKNOWN ≠ INCOMPLETE`; insufficient evidence means the correct state remains UNKNOWN.

## 3. Production implementation

### Recovery function

Exact signature:

```sql
public.correct_enrollment_start_date(
  p_enrollment_id uuid,
  p_start_date date,
  p_reason text,
  p_evidence_note text
) RETURNS jsonb
```

Security/runtime contract:

- owner: `postgres`;
- `SECURITY DEFINER`;
- `search_path = ''`;
- EXECUTE: `authenticated`, `service_role`, `postgres`;
- no EXECUTE: `anon`, `PUBLIC`;
- authenticated actor must resolve to `master_admin` or `sub_admin` and the derived school must be in `user_school_ids()`;
- teacher, parent, child/student, cross-school operator, platform operator, and unauthenticated caller are not authorized by the internal gate;
- known `start_date` always rejects with `start_date_already_known`, including an identical repeat value;
- NULL proposed date, missing/oversize reason or evidence, proposed start after known end, M3 overlap, and invalid geometry fail closed;
- the audit event is `enrollment_start_date_corrected` and records actor/entity/school/class/child/reason plus old/new start, end, state, operation, and evidence note;
- audit failure is intentionally uncaught so the enrollment UPDATE rolls back atomically.

### Direct UPDATE hardening

M1 revoked table-level UPDATE from `authenticated` and `anon`, then restored authenticated column-level UPDATE only for:

```text
child_id, class_id, school_student_code, state, end_date, updated_at
```

Therefore `authenticated` and `anon` cannot directly UPDATE `start_date`. Existing RLS continues to govern permitted non-start row updates, and legitimate non-start UPDATE capability remains available to `authenticated`.

### M3 preservation

M1 did not weaken or bypass either M3 invariant:

- `enrollments_valid_interval_chk` still rejects known geometry where `end_date < start_date`;
- `enrollments_no_overlap_excl` still rejects overlapping known intervals for the same `child_id + class_id`.

The recovery RPC relies on these database constraints as the final backstop. Overlap/check failures do not leave a partial correction or audit.
