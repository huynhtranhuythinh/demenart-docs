## 1. CANONICAL UNDERSTANDING

**Two independent gates exist live inside `execute_mission_control_action`, not yet reconciled:**

- **Gate A — Authority Gate (B9.4).** `mc_internal._mc_authority_gate` → pass-through to `_resolve_authority`. Placed **after** object-context resolve, **before** `_mc_begin_action`. Fires only when registry `authority_gated=true`. Deny = `MC_ACTION_PERMISSION_DENIED` + reason_codes, **0 ledger · 0 mutation**. Currently gated: `class.edit` (LOW) only.
- **Gate B — Decision Gate (B7).** `_mc_open_decision` + decision read. Placed **after** `_mc_begin_action`, **before** adapter CASE. Routed by `risk_level`: LOW/MEDIUM → adapter (auto); HIGH/CRITICAL → open decision → **park** (ledger stays `processing`, C-4). Decision states `{pending, approved, rejected, expired, cancelled}`. **DORMANT** — no HIGH/CRITICAL action registered; decisions/transitions = 0/0.

**Decision Lifecycle Foundation (B8).** `mc_internal._mc_transition_decision(uuid,text,uuid,text)` (md5 `fe0eea59…`) = the single decision-state mutation boundary (FOR UPDATE lock + legal-edge validation + terminal protection + append-only evidence). `mission_control_decision_transitions` = append-only, trigger-enforced for all roles incl. `service_role`. Invariant: **Registry = WHAT · Adapter = HOW · Decision = WHETHER · Ledger = execution truth · Memory = projection.**

**Authority Resolver contract (B9.1 frozen · B9.2 ratified, D366).** `_resolve_authority(actor, capability/action_key, object_context, decision_context) → { eligible, authority_source, reason_codes }`. Pure · deterministic · read-only · explainable · **consumed-not-embedded**. `capability/action_key` = PRIMARY anchor (D366.3, path-symmetry). `decision_context` = SECONDARY, optional — carries **requester identity + self-approval rule + decision phase** (absent on direct-execute, present when a decision wraps the action). Single-source is of the **policy verdict**, NOT of "authorization" (D366.4 · CTO Correction 1) — RLS + adapter domain-safety + lifecycle controller still enforce independently. Vocabulary is **draft/controlled-text, NOT minted** (D366.6). In-use reason_codes include `self_decision_forbidden`, marked **"resolver-tier only"** in v1.56 — i.e. the resolver body already carries the branch, but **no production decision path consumes it yet.**

## 2. CURRENT ARCHITECTURE GAP

**Authority evaluation is asymmetric across the two authority questions:**

| Authority question | Where evaluated today | Resolver-sourced? |
|---|---|---|
| **Requester authority** — "who may *request* execution of this action on this object?" | Gate A (`_mc_authority_gate` → `_resolve_authority`), before `begin_action` | ✅ **Yes** (for gated actions; live since B9.4) |
| **Approver authority** — "who may *approve / reject / cancel* this decision?" | Embedded inside decision RPCs (`resolve_mission_control_decision`, cancel path): `master/sub + same-school + not-self` string logic (B7) | ❌ **No** — legacy embedded |

**Consequence:** `authority_gated=true` is honest only for the **requester** side today. The **approver** side is still a parallel, hand-rolled authority engine living in the decision RPCs — exactly the duplication B9.1 flagged (Risk 3 policy divergence, Risk 4 self-approval regression). The resolver *already* exposes `self_decision_forbidden` at the resolver tier, but the decision layer re-derives self-approval prohibition in its own strings instead of consuming that verdict.

**What B10.1 closes:** migrate the approver-side authority evaluation out of the decision RPCs and into consumption of `_resolve_authority`, so a **single primitive** answers both authority questions.

**What B10.1 deliberately does NOT do:** it does **not** arm Gate B. The decision lifecycle stays dormant (0/0). The migrated approver path is exercised **only by rolled-back JWT-impersonated rehearsal** (B7/B8 method) — same epistemic status as B7/B8: **no over-claim of "proven on committed data."** The first committed decision is a separate, later, explicitly-authorized milestone.

## 3. DECISION AUTHORITY RESOLUTION DESIGN

### 3.1 Authority boundary reconciliation (Q1)

**Inside `_resolve_authority` (the VERDICT — both questions):**
- Requester eligibility (WHO may request) — already consumed by Gate A.
- Approver eligibility (WHO may approve/reject/cancel) — **new consumption**, driven by `decision_context = { decision_phase, requester_id }`.
- `authority_source` + `reason_codes`, including phase-conditional `self_decision_forbidden`.

**Outside the resolver (unchanged — never pushed in):**
- Decision **state machine** and **transition legality** — `_mc_transition_decision` (allowed edges, terminal protection, ROW_COUNT assertion, evidence insert).
- **Adapter domain validation** — FK validity, entitlement/scope invariants, dedup (defense-in-depth, D366.4).
- **RLS** row-visibility floor (`select_own`).
- **Intent-integrity guards** — `intent_fingerprint` UNIQUE + original-actor guard (C-2). These are replay/identity-integrity controls, **not** authority verdicts; they stay in the executor/RPC, not in the resolver.

### 3.2 Execution ordering (Q3) — recommendation: **Option B (dual-consultation)**

Option A (`Request → Decision Lifecycle → Authority Resolver → Mutation`) is **rejected**: a single authority check placed *after* the lifecycle has no seam at which to gate the **approve action itself**, and the only way to make it work is to push approver-authority into `_mc_transition_decision` — polluting the B8 mutation-only boundary (Risk 6). It also opens a decision row for a requester whose authority has not been established, inviting inbox pollution and orphan evidence.

Option B (`Request → Requester Authority → Decision Lifecycle → Approver Authority → Mutation`) is **recommended**: two authority questions at two phases, both routed through one primitive.

| Criterion | Option A | **Option B ✅** |
|---|---|---|
| **Security** | Approver authority homeless or forced into the lifecycle controller; unauthorized requester can open decisions | Unauthorized requester denied before any decision row (Gate A, 0-residue proven); unauthorized approver denied before `transition(approved)` |
| **Auditability** | Evidence rows can precede an authority verdict | Every decision row and every transition is backed by a resolver verdict; deny = structured rejection, not a parked row |
| **Idempotency** | Verdict computed after park; replay reasoning muddied | Deterministic verdict up-front on both phases; `intent_fingerprint` dedup preserved; replay → same verdict |
| **Rollback** | May have written decision + evidence before discovering ineligibility | Deny-before-mutation on both phases; 0 residue (B9.4 class.edit deny is the proof shape) |
| **Complexity** | Approver authority stays embedded, or B8 boundary is violated | One primitive, two phases; decision RPCs shrink to lifecycle mechanics + resolver call |

### 3.3 Post-B10.1 control plane (Q7)

```
Action Request
  → Requester Authority  ── _resolve_authority (Gate A, EXISTING) ── DENY→ 0 ledger·0 mutation
  → _mc_begin_action
  → Decision-required?  (risk_level routing, Gate B)
       ├ LOW / MEDIUM ─ no decision ─→ adapter → _mc_commit_action        (auto path)
       └ HIGH / CRITICAL ─→ _mc_open_decision (park; ledger processing)
                                  … approver arrives …
             → Approver Authority ── _resolve_authority(phase=approve,     ── DENY→ no transition
                                       requester_id) (MIGRATED — B10.1)
             → _mc_transition_decision(approved)   (B8 boundary, UNCHANGED)
             → resume → adapter → _mc_commit_action
```

**Verification of the three target invariants:**
- **No authority duplication** — requester + approver authority both resolve through `_resolve_authority`; embedded `master/sub + same-school + not-self` strings removed from decision RPCs.
- **No decision leakage into adapter** — the adapter (`class_edit_v1`, `assign_class_distribution`, …) never reads decision state; it runs only on the approved-resume path and keeps domain-safety only.
- **No resolver mutation responsibility** — `_resolve_authority` stays read-only; all mutation remains in `_mc_transition_decision` (decision state), the adapter (business object), and the ledger.

## 4. DECISION CONTEXT CONTRACT (Q2)

Candidate inputs evaluated against the frozen resolver signature `(actor, action_key, object_context, decision_context)`:

| Input | Verdict-relevant? | Disposition |
|---|---|---|
| `actor_id` | Yes — the identity whose authority is evaluated (requester at request-phase, approver at decide-phase) | **Resolver param `actor`** (already frozen) |
| `action_key` | Yes — PRIMARY authority anchor (D366.3) | **Resolver param `action_key`** (already frozen) |
| `object_context` | Yes — org scope + typed object; cross-school leakage guard (Risk 5) | **Resolver param `object_context`** (already frozen) |
| `requester_id` | Yes, at decide-phase only — evaluates `requester ≠ approver` | **In `decision_context`** |
| `decision_phase` | Yes — distinguishes request / approve / reject / cancel; governs whether self is forbidden or allowed | **In `decision_context`** |
| `decision_id` | **No** — a lifecycle handle, not a policy input. Passing it risks coupling the pure resolver to mutable lifecycle rows and breaking determinism | **NOT in resolver contract** (caller's handle) |
| `request_id` | **No** — a ledger handle, same reasoning | **NOT in resolver contract** (caller's handle) |

**Recommended minimal immutable `decision_context` = `{ decision_phase, requester_id }`.**
- `requester_id` is meaningful only when `decision_phase ∈ {approve, reject}`; ignored at `request` phase.
- **Immutability discipline:** `requester_id` is bound at decision-open (the decision row's opener) and passed to the resolver **as data**. The resolver **never re-derives** it from mutable state — preserving determinism and read-only purity. `decision_phase` is a caller-declared constant per call site.
- **Design assumption to confirm at implementation-D1 (not asserted here):** whether the live `_resolve_authority` body already accepts and branches on `decision_phase` + `requester_id` (the `self_decision_forbidden` "resolver-tier only" marker suggests the branch exists). If yes, B10.1 is **consume-only** and `_resolve_authority` body stays byte-unchanged (the D368.3 pattern). If the branch is a stub, that is a scoped resolver change to be surfaced explicitly, not smuggled.

## 5. AUTHORITY GATE SEMANTICS (Q4)

**Recommendation: `authority_gated` = meaning A — "this action's authority verdict comes from the Authority Resolver."** Authority axis only.

- **Reject B** ("requires Decision Lifecycle"): conflates two orthogonal axes. `class.edit` is authority-resolved **and** auto-executes (LOW, no decision) — meaning B cannot express that shape.
- **Reject C** ("requires full policy pipeline"): collapses a 2-D space into 1-D and destroys the ability to reason about which specific control applies.

**Why Authority and Decision must stay separate axes:**
- **Authority** (WHO may) is evaluated per-actor, per-phase, by the resolver.
- **Decision** (WHETHER a *second human* must approve) is a **risk property** of the action, expressed by `risk_level` (LOW/MED = auto; HIGH/CRIT = decision lifecycle).
- The full action space is the 2×2 product: `{gated, ungated} × {auto, decision}`. `class.edit` = `{gated, auto}`; a future `child.transfer` = `{gated, decision}`; `class.assign` today = `{ungated, auto}`. A "policy pipeline" is the **emergent composition** of the two flags — never a single flag.

**Honest note:** meaning A becomes **complete** only after B10.1 (both requester- and approver-authority resolver-sourced). Before B10.1, `authority_gated=true` is honest for the requester side alone. B10.1 is precisely what makes the semantics true end-to-end.

## 6. DECISION RPC MIGRATION BOUNDARY (Q5 + Q6)

### 6.1 Which legacy checks move (Q5)

| Surface | Disposition in B10.1 |
|---|---|
| `mc_internal._mc_open_decision` | **Mechanically unchanged.** Requester authority is already established upstream by Gate A before the decision opens (ordering §3.3). Open records `NULL→pending` evidence as today. The `no_eligible_approver` pre-check (B7 CE15) is a **scope-enumeration** concern (does any eligible approver exist in scope?), not a per-actor verdict — keep as-is; may later be made resolver-consistent, out of B10.1 scope. |
| `resolve_mission_control_decision` (approve / reject) | **MIGRATE.** Replace embedded `master/sub + same-school + not-self` with one call: `_resolve_authority(approver, action_key, object_context, {phase:'approve'|'reject', requester_id})`. Map `self_decision_forbidden → MC_*`, `role_not_eligible / organization_scope_mismatch → not_authorized_to_decide`-class surface. Write still delegated to `_mc_transition_decision` (B8). |
| Cancel path | **MIGRATE policy, PRESERVE semantics.** `phase='cancel'`: the **opener is ALLOWED** to cancel their own request (opposite of self-approve). The resolver distinguishes phase, so self-cancel is not blocked while self-approve is. Non-opener (e.g. admin) cancel = a separate resolver verdict. |
| Decision inbox visibility | **SHOULD become resolver-consistent** (Risk 3: inbox must not surface a decision that `resolve` would then deny). Hard B10.1 requirement is the **resolve/cancel verdict**; full inbox-projection rewrite may be a verify-only step or a deferred sub-item — flagged, not force-fit. |

### 6.2 Preserved untouched
- `_mc_transition_decision` boundary (mutation-only; md5 `fe0eea59…` frozen).
- Append-only decision history (`mission_control_decision_transitions` + block trigger).
- Terminal-state protection (`*→pending` blocked; non-pending write blocked).
- Original-actor guard (C-2) + `intent_fingerprint` UNIQUE — intent integrity, executor level.
- RLS `select_own` row-visibility floor.

### 6.3 Self-approval prevention (Q6) — single resolver-based mechanism

- **One rule, one place:** the resolver evaluates `requester_id == actor_id AND phase ∈ {approve, reject}` → `eligible=false, reason_codes=[self_decision_forbidden]`. No duplicated string checks; no scattered RPC conditions. The RPC calls the resolver and maps the reason_code to its error surface.
- **Phase-conditional, not blanket:** self-**cancel** is allowed; self-**approve/reject** is forbidden. `decision_phase` is what lets a single primitive get both right — this is the design reason `decision_phase` is mandatory in the context contract.
- **requester_id provenance:** bound at decision-open (immutable opener), passed as data; the resolver never re-derives it.
- **Defense-in-depth retained (D366.4):** single-source governs the **verdict**, not sole enforcement — RLS `select_own` and the C-2 original-actor guard remain independent floors.
